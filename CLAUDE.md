# Phoenix (Ejara admin panel) automation — conventions for AI changes

Playwright + TypeScript tests of Phoenix, the Ejara admin panel. Its test plan lives in the **Ejara Automation Tool**;
this repo follows it (spec §6.9.5 of the tool). Changes made by AI always go through a pull request reviewed by QA.

## Structure
- `test-plan/*.json` — **generated by the tool, never edited by hand.** (`src/test-plan/*.plan.json` is the former
  plan, used by `tc()` until the tool's plan is applied.)
- `tests/<module>/` — one `test()` per case: `test('<TC ID> <what it checks>', tc('<TC ID>'), async (…) => { … })`.
- `src/pages/` — page objects and components (`src/pages/components/`). `src/fixtures/` — fixtures.
  `src/reporting/` — reports (session reports, runner results).
- `ejara-automation.json` — what the tool reads (commands, folders).

## What a task may change
A task names its TC IDs. Change only the tests of those TC IDs in `tests/` and the page objects they use in
`src/pages/`. `playwright.config.ts`, fixtures, reporting, scripts and other modules' tests need a task that says so.
Never edit `test-plan/`.

## Rules
- Every test uses `tc('<TC ID>')` with an ID of the plan; it checks the case's steps and expected results. If the
  panel differs from the case, say so in the PR: don't change the expectation. Known bugs keep the `@known-bug` tag.
- Tests share one admin session and run sequentially (`workers: 1`): no test logs out or changes the shared session.
- Money operations (manual deposit / withdrawal) only on testbox, with the test data in `src/fiat/test-data.ts`.
- No secrets in code: credentials come from `.env` (see `.env.example`).

## Before the pull request
`npm run typecheck`, `npm run test:unit`, then run the changed tests once on testbox and attach the result.

## Catalog (catalog.json) and executor
`catalog.json` is the vocabulary the tool's test cases are written in: page objects of `src/pages/` (id = fixture name
in `src/fixtures/test-fixtures.ts`, else the class name), their public `Locator` properties (elements) and public async
methods (actions). It is **generated** by `npm run catalog`, never edited by hand: any change to a page object must
regenerate it in the same pull request (the `catalog.json is up to date` unit test fails otherwise). Name elements by
what they are (`…Button`, `…Input`, `…Tab`, `heading`) so their kind is right in the tool.

A method that moves money gets `@movesMoney` in its JSDoc, one that changes a customer account gets `@changesState`:
the catalog marks it and the elements it uses, and the executor never runs them unless `PHX_ALLOW_MONEY_OPS` /
`PHX_ALLOW_ACCOUNT_OPS` allow it.

`src/executor` runs the tool's Runnable cases from their automation steps (`tests/tool/run-plan.spec.ts`, only when the
runner gives a run plan in `EJARA_RUN_PLAN`), on the page objects the catalog names. Keep it free of app knowledge:
a missing word belongs in a page object, not in the executor.
